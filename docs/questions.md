# Q. event를 추가, 제거하고 저장하는 로직을 그대로 구현할 경우 발생할 수 있는 문제점

- 비동기 요청과 상태 동기화 문제
  이벤트 추가나 삭제 후에 서버로부터 데이터를 재요청(fetch)하는 로직이 있다면, 비동기 요청의 응답 순서가 예상과 다르게 처리될 수 있습니다. 이로 인해 최신 상태가 제대로 반영되지 않거나, 중복된 데이터가 들어오는 등의 상태 불일치 문제가 발생할 수 있습니다.

- Race Condition 발생 가능성
  동시에 여러 이벤트 조작(추가/수정/삭제)이 발생할 때, API 호출의 응답 타이밍이 서로 겹치면 최종 상태가 올바르게 업데이트되지 않을 위험이 있습니다. 예를 들어, 이벤트 삭제 후 재요청(fetch)하기 전에 다른 변경 사항이 적용되면, 삭제된 이벤트가 다시 목록에 노출될 수 있습니다.

- 테스트 독립성 및 신뢰성 저하
  여러 테스트 케이스가 동일한 상태 업데이트 로직을 공유하는 경우, 한 테스트에서 상태 변경이 다른 테스트에 영향을 미쳐 예상치 못한 결과를 초래할 수 있습니다. 이는 테스트 독립성을 해치고, 테스트 간 데이터 격리가 어려워지는 문제로 이어집니다.

- UI와 서버 간 불일치
  UI에서는 사용자가 이벤트 추가/삭제를 진행할 때 즉각적인 피드백을 기대하지만, 서버와의 동기화 과정에서 잠시라도 잘못된 정보가 노출되거나, 응답 지연으로 인해 업데이트가 늦어질 수 있습니다. 이는 사용자 경험에 부정적인 영향을 줄 수 있습니다.

- 유지보수성 및 코드 복잡도 증가
  단순히 이벤트를 추가하거나 제거한 후 즉시 재요청(fetch)을 하는 방식은 코드가 복잡해지기 쉽습니다. 이후 기능 확장이나 리팩토링 시, 의도치 않은 사이드 이펙트가 발생할 가능성이 높아지고, 버그를 추적하기 어려워질 수 있습니다.
  이러한 문제들을 해결하기 위해서는, 상태 업데이트와 API 호출 간에 명확한 제어 로직을 두거나, optimistic 업데이트 방식, 또는 API 응답에 따른 명시적인 상태 갱신 전략을 마련하는 것이 필요합니다.
